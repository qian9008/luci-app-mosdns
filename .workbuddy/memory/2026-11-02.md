## 事故：pack-luci.sh 打包把路由器 `/` 权限改成 0700 501:dialout

**用户反馈**：路由器重启后系统"坏了，只能进临时系统"，`upper` 根目录权限 `drwx------ 501:dialout`。

**根因（我的 bug，确认）**：

`tools/pack-luci.sh` 用 `tar -C "$TMP" .` 打包，`$TMP` 是 `mktemp -d` 创建的，权限 `0700`、属主 `qian:staff`（macOS `501:20`）。包里因此带一条 `./` 条目，属性 `0700 501:20`。

用户在路由器上 `cd / && tar xzf`，root 执行 tar 会忠实恢复这条条目：`chmod 700 /` + `chown 501:20 /`。`/` 是 overlayfs 合并视图，改动落到 upperdir 根，`/overlay/upper` 变成 `0700 501:dialout`。Linux 上 gid 20 = `dialout`，与现象完全吻合。

下次启动 overlay 挂好后 `/` 继承该属性，非 root 进程无法遍历根目录 → 系统崩溃。

**修复**：

- 改用 Python `tarfile` 打包，只遍历 `www`/`etc`/`usr`，不产生 `./` 条目
- 所有条目强制 `uid=gid=0`、`uname=gname=root`
- 目录统一 755，文件按可执行位给 755/644
- 自检加两条硬规则：无 `./` 条目、全部 uid=gid=0（用 Python 读，`tar tzvf` 的列在 bsdtar/GNU tar 下不一致，`awk '{print $2}'` 是坑）
- 自检路径前缀去掉了 `./`（Python 打包 arcname 是 `www/...` 不是 `./www/...`）

**用户已自行恢复**：`chown root:root` + `chmod 755` upper 根目录后重启，系统正常，501 残留 0 个。

## 附带查清的另一个问题：PVE 磁盘枚举时序

故障期间发现系统用了临时的 loop0（250MB f2fs）overlay，而不是真实的 1.5GB ext4 盘。

`dmesg` 证据：

```
[  6.0s] mount_root: switching to f2fs overlay      ← 6 秒完成 overlay 挂载
[641.6s] sd 0:0:0:0: [sdb] ... 1.61 GB             ← sdb 10 分 42 秒后才出现
```

系统在开机第 6 秒找 overlay，sdb 第 641 秒才被内核枚举。这台是 PVE/QEMU 虚拟机（两块 virtio 盘），sdb 所在的存储就绪慢，`mount_root` 等不及就 fallback 到镜像自带空 overlay，表现为"系统回到出厂状态"。

**待办（用户侧）**：去 PVE 把 1.5GB 那块盘的存储从目录/NFS/iSCSI 迁到 `local-lvm`，否则每次重启都可能重现。另外 `sdb1/upper/etc/config/fstab` 里 `/overlay` 的 UUID 写的是 `ff313567-...`，与实际 `e0bcc5b5-...` 不符，是历史遗留。

## 事故：route.uc 从未真正跑通过（两个连环 bug）+ 上游选域名导致超时

**用户反馈**：规则里配了 chatgpt.com / openai.com / google.com，实际却走远程 DNS。

**排查（SSH 到 192.168.50.9 实测，不再靠猜）**：

1. `uci show mosdns` 有 `config route '2'`，规则内容正确 → 不是 UI 保存问题
2. `/var/etc/mosdns.base.json` 与 `mosdns.json` 字节数完全相同（6915）→ route.uc 没做任何改写
3. 手动执行 `route.uc` 直接抛错退出码 254：
   `Reference error: left-hand side expression is not an array or object` at `r.enabled`
4. `logread` 里只有 `route.uc failed, custom routes skipped`，被 init.d 的 `|| logger` 吞掉了真实原因

**Bug 1（致命，一版就废）**：ucode 的 uci 游标 `c.get(config, section)` 不传第三个参数时，
返回的是 **section 的类型名字符串**（`"route"`），不是 section 对象。用 `@route[N]` 语法也一样。
`read_routes()` 拿它当对象取属性 → 崩溃 → 规则永远不生效。
修复：改用 `c.foreach('mosdns', 'route', cb)`，且回调必须 `return null;`
（`push()` 返回数组长度，非 null 会中断遍历，只读到第一条）。

**Bug 2（可观测性）**：init.d 里 `$ROUTE_SCRIPT || logger -t mosdns "failed, skipped"` 把崩溃原因丢了。
修复：`$ROUTE_SCRIPT 2>&1 | logger -t mosdns`，成功记 `N rule(s) applied`，失败记完整报错栈。

**Bug 3（换上游后暴露）**：修好注入后，三个域名全部 5 秒超时。逐层隔离（最小配置 t1~t8 对照）：

| 配置 | 结果 |
|---|---|
| `https://dns.quad9.net/dns-query` + bootstrap | 间歇 FAIL（6 次里 4~5 次失败） |
| `https://dns.quad9.net/dns-query` + `bootstrap_version: 4` | 仍然 5/6 失败 |
| `https://dns.quad9.net/dns-query` + `dial_addr: 9.9.9.9` | 5/5 OK |
| `https://9.9.9.9/dns-query`（IP 直连） | 稳定 OK |
| `quic://94.140.14.14` / `quic://dns.adguard-dns.com` | 全 FAIL（此线路不可达） |

根因：quad9 的 DoH 域名解析出两个 A 记录，**`149.112.112.112:443` 在这条线路上直接超时**，
`9.9.9.9:443` 正常。mosdns 不过滤不可达地址，命中坏 IP 就是 `TLS handshake timeout`。
日志里表现为 `upstream error ... TLS handshake timeout` + `all upstream servers failed`。

顺带排除了两个误判方向：本机 IPv6 出网不通（`curl -6` 2ms 失败）但不是主因；
SNI 阻断也不成立（`--connect-to` 带 `dns.quad9.net` SNI 连 9.9.9.9 仍然 0.17s 通）。

**修复**：

- UI 预设全部改 IP 形式：`https://8.8.8.8/dns-query`、`https://1.1.1.1/dns-query`、
  `https://9.9.9.9/dns-query`（证书都有 IP SAN，`curl` 裸校验已验证通过），
  删掉不可达的 AdGuard DoQ 预设
- 用户配置 `mosdns.2.upstream` 改为 `https://9.9.9.9/dns-query`
- 文案加提示：手填域名需要 bootstrap 解析，可能解析到不可达地址

**验证（注入 + 生效双证据）**：
- `route.uc: 1 rule(s) applied`，配置 6915 → 7502 字节
- main_sequence 第 13 项是 `$route_seq_1`，位于 reject 之后、greylist 之前 ✓
- 开 info 日志取证：`chatgpt.com` 命中 `route_set_1 → route_seq_1 → route_up_1 → route_fwd_1`，
  对照域 `github.com` 走 `forward_remote` ✓
- 三个规则域名连测 3 轮全 OK

**本次改动**：`route.uc`（read_routes）、`init.d/mosdns`（日志）、`route.js`（预设 IP 化 + 文案）、
`po/zh_Hans`（1 条）、`PROJECT_wiki.md`（第 4 节加第 5 条约束 + ucode uci 两个坑）。

## Bug：规则页整块重复渲染（加 config route 之后暴露）

**现象**：`/admin/services/mosdns/rules` 出现上下两份完全一样的标签栏 + 文本框。

**根因**：LuCI 的 `CBIAbstractSection.__init__(map, sectionType)` 直接把 `sectiontype`
设为第二个参数，`new form.TypedSection()` 不传就是 `undefined`；而
`data.sections(config, sectiontype)` 的判断是 `sectiontype == null || ...`，
等于返回配置文件里**所有** section。以前 `/etc/config/mosdns` 只有 `config mosdns` 一个
section，所以只渲染一遍；加了 `config route '2'` 后变两个，页面就变成两份 ——
而且每多一条路由规则就多一整块。

**修复**：
- `rules.js`：该页只读写文件不碰 UCI，传虚拟类型 `'rules'` 并固定 `cfgsections = () => ['rules']`
- `update.js`：选项属于 `config mosdns`，显式传 `'mosdns'`
- `basic.js:109` 的 TypedSection 因为整段重写了 `render()`，不受影响，未改

**验证方法（可复用）**：本机 Chrome headless 加 `--no-sandbox` 才能在工具沙箱里起来；
LuCI 的 cookie 名是 `sysauth_http`（不是 `sysauth`），而且 `session_retrieve` 要求
session values 里有 `token`，所以必须 `session login`（本机 root 空密码可登录）
+ `session set values.token`，否则 403。用 CDP 打开页面后统计 DOM 元素数量最可靠：
修复前 tabmenu=2/textarea=16，修复后 tabmenu=1/textarea=8。

## 需求：自定义路由域名不走「Cloudflare 优选 IP」

**问题**：`has_resp_sequence` 里有一步
`resp_ip $cloudflare_cidr → black_hole $cloudflare_ip`，只排除了
whitelist / greylist / stream_media。自定义路由命中后 `jump has_resp_sequence`，
所以用 9.9.9.9 查 chatgpt.com 拿到的真实 IP 会被替换成用户填的 cloudflare_ip。

**错误方案（已验证会炸）**：往那一步的 matches 里加 `!qname $route_set_N`。
mosdns 按配置顺序 Init 插件，sequence 的 qname matcher 在 Init 时就要求
domain_set 已存在 —— 前向引用直接 `cannot find domain set myset` 启动失败。
而 has_resp_sequence（index 24）排在 route_set_1（index 36）之前，改不了。
最小复现：`{"sequence":{"matches":"qname $myset"} → forward → domain_set myset}`。

**正解**：复制一份 has_resp_sequence、只删掉 CF 那一步，生成 `route_resp_sequence`，
main_sequence 里改成 `jump route_resp_sequence`。没开 CF 优选时不生成，退回原来的
`has_resp_sequence`。复制而非照抄的意义：TTL 相关步骤仍从 base.json 读，用户改全局设置自动跟随。
识别 CF 步骤的特征：exec 以 `black_hole` 开头 **且** matches 里带 `$cloudflare_cidr`
（query_is_reject_domain 也用 black_hole 做拦截，不能只看 exec）。

**验证**：chatgpt/openai/google 返回上游真实 IP；cloudflare.com 仍被改成 104.17.149.12。
⚠ 改完必须重启，旧缓存会把改写后的结果留 24h（lazy_cache_ttl），看起来像没生效。

**顺手清理**：设备上残留 25 个测试用 mosdns 进程（`-c /tmp/t*.json`），
因为 busybox 没有 pkill、脚本里的 `kill %1` 在非交互 sh 下无效。以后测试进程用
`for p in $(pgrep mosdns); do ... /proc/$p/cmdline ... kill` 显式清。
