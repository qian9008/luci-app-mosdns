# 2026-11-01

## CI 改造：release-build.yml 支持手动选架构

**背景**：原 workflow 只有 `on.push.tags`，没有 `workflow_dispatch`，所以 Actions 页面没有 "Run workflow" 按钮；本地也从未打过 tag，因此一次都没跑过。

**改动**（`.github/workflows/release-build.yml` 全量重写）：

- 增加 `workflow_dispatch`，三个输入：`arch`（自由文本，空=精选/all=全部/单值）、`tag`（choice）、`release_tag`（可选，留空则只产生 Actions artifact，不创建 Release）
- 新增 `prepare` job，用内嵌 Python 生成动态 matrix：`ALL_ARCHES`(32) / `DEFAULT_ARCHES`(9) / `ARCH_ALIAS` / `SKIP` 四份数据集中在 prepare
- 把原来的 `EFFECTIVE_ARCH` 映射和 `SKIP_BUILD` 判断从 build job 的 shell 分支前置到 prepare，无效组合不再启动 runner
- push tag 触发改为跑精选 9 架构 × 2 版本 = 18 job（原来 32×2=64）
- build job name 改为 `${{ matrix.pkg_arch }}`，tar 包名同步

**保留的坑**：`actions/checkout@v6`、`sbwml/openwrt-gh-action-sdk@go1.27` 未动；打包步骤保留 `continue-on-error`。

**验证**：本地用 PyYAML 解析确认结构合法，并用 8 组环境变量组合跑通内嵌脚本（push/精选/单架构/all+all/无效组合/别名映射/错误架构名/指定 release_tag）。all+all 输出 63 job（64 - mips_4kec@25.12）。

**分支与提交**：新建本地分支 `dev`（从 `v5` 的 `dbdd91a` 拉出），拆成两个 commit 并推送到 `origin/dev`：

- `661a2af` ci: 支持手动选择架构编译，push tag 改为精选架构矩阵（含 PROJECT_wiki.md、.workbuddy/memory）
- `aeab7eb` luci-app-mosdns: 新增自定义上游分流功能（route.js / route.uc / init.d / rpcd / menu / acl / po）

**关键坑（已解决）**：GitHub 只在**默认分支**上注册 `workflow_dispatch`。本仓库默认分支是 `v5`，仅在 `dev` 上加 `workflow_dispatch` 不会让 Actions 出现 Run workflow 按钮。

解决方案选了「把 CI 改动同步到 `v5`」而不是改默认分支。`v5` 现有历史：

- `e963de7` ci: 支持手动选择架构编译（用户自己先推上去的，等同 dev 的 `661a2af`）
- `f8ca05f` ci: 架构改为下拉选择，默认 x86_64 + openwrt-25.12

同步方式没用 cherry-pick，而是 `git checkout v5 && git checkout dev -- <文件> && git commit`，直接把最终状态落成一个增量 commit，避免中间态。
`.workbuddy/` 只在 dev 上，v5 不含（v5 是上游同步镜像，保持干净）。

**注意**：`v5` 已不再是纯上游镜像，以后同步上游 rebase 时这两个 CI commit 会带过来，`.github/workflows/release-build.yml` 可能冲突。

**待办**：在 Settings → Actions → General 确认 Actions 已启用。

## CI 修复：tar 找不到 bin/packages/x86_64

**根因**：SDK 步骤从来没传 `ARCH`。不是重构弄丢的——`git show dbdd91a` 确认最初版的 env 里就只有
FEEDNAME / PACKAGES / NO_REFRESH_CHECK，重构时照抄了这个缺失，所以这个 workflow 从诞生起就没成功产出过包。

`sbwml/openwrt-gh-action-sdk` 的 Dockerfile 是 `ARG ARCH=mips_24kc` + `FROM $CONTAINER:$ARCH`，
不传就默认 `mips_24kc`。于是每个 job 都编出 MIPS 包，产物在
`bin/packages/mips_24kc/packages_ci`，而 `tar -C bin/packages/<目标架构>/` 必然报
`Cannot open: No such file or directory`。编译步骤是绿的，`continue-on-error` 又把错误吞了，日志完全指不到真凶。

**修复**：编译步骤加 `ARCH: ${{ matrix.pkg_arch }}`（= 有效架构-版本，如 x86_64-openwrt-25.12）；
打包步骤去掉 `continue-on-error`，改为目录不存在时 `::error::` + 打印 bin/packages 结构后退出。

**镜像 tag 已验证**（ghcr.io/v2/openwrt/sdk 逐 tag 探测 32 架构 × 2 版本）：格式是 `<arch>-openwrt-<branch>`，
带 `openwrt-` 前缀；`x86_64-25.12` 这种无前缀写法是 404。实测正好 3 个组合缺失：

| 缺失组合 | 处理 |
|---|---|
| openwrt-25.12 + mips_4kec | `SKIP` 剔除 |
| openwrt-25.12 + riscv64_riscv64 | `ARCH_ALIAS` → riscv64_generic |
| openwrt-24.10 + riscv64_generic | 无需处理（24.10 本就用 riscv64_riscv64） |

SKIP 与 ALIAS 表由此确认正确，缺失的只有 `ARCH` 传参。

**教训**：三个名字别混 —— arch（用户视角）/ effective_arch（bin 目录名，经 ARCH_ALIAS 映射）/
pkg_arch（镜像 tag + tar 文件名）。packages 输出目录用的是 effective_arch，镜像 tag 用 pkg_arch。
